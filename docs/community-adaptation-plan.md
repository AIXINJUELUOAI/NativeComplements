记录日期：2026-11-16

## 一、主线与任务分支

后续采用稳定主线与短期任务分支：

- `main` 用于经过审查的集成与发布。
- 功能、适配、修复均在对应任务分支开发，完成必要测试与 Review 后合入主线。
- 分支按任务建立，合并后结束，不维护长期分叉的不同 ROM 产品线。
- 具体分支命名、合并方式与检查项在正式启动时确定，不在当前提前搭建流程。

## 二、社区适配提交与责任

基本流程：用户适配 → 提供测试记录 → 我们 Review → 通过后合入主线 → 登记适配名单。

- 对外以“某用户适配了某系统”表达贡献归属，不向普通用户展示组件／能力矩阵。
- 适配提交须说明系统版本、相关组件、已测试范围、已知限制及反馈入口，供 Review 和维护使用。
- 适配者确认署名和兼容性问题的承接方式，反馈入口优先使用其维护的仓库 Issue 等公开渠道，不默认公开私人联系方式。
- 对应系统的兼容性问题优先引导至适配者；主项目负责共用功能、公共逻辑和集成，不承诺替没有设备、资料和测试条件的系统完成兼容性排查。
- 适配者停止维护时，记录并提示“暂停维护”，不继续提供失效的反馈承诺。
- 适配记录不等于所有功能已验证；具体未验证项与限制保留在适配说明中，不堆在首页。

## 三、普通用户看到的内容

### 匹配已有适配

首次进入模块主页时，只展示当前系统对应的一条简洁提示，例如：

> 当前系统由 @某某 提供适配。
> 该系统的兼容性问题，请优先向适配者反馈。
> 入口：适配说明与反馈。

不在首页罗列所有适配者、全部系统或逐功能的适配明细。

### 没有适配记录

> 当前系统暂无社区适配记录，部分功能可能无法正常使用。
> 入口：了解如何参与适配。

没有名单记录不等于所有功能均不可用；有记录也不代表系统更新后所有功能仍然有效。

### Hook 检查与功能提示

- Hook／能力预检及具体技术信息留在内部，不向普通用户展示类名、方法名或 Hook 点列表。
- 优先复用各宿主已有的接入预检和受限状态上报，不在主页进程假装扫描全部系统进程。
- 确认某功能缺少必要接入能力时，只在对应功能页面显示“当前系统暂不支持此功能”等可理解提示。
- 功能关闭、尚未收到检查结果与确定不支持必须区分，不能将未知状态当作不可用。
- 首次提示及升级后重新匹配的具体展示方式留待实施时确定，避免反复弹窗。

## 四、代码与文档改组原则

- 延续“平台事件输入 → 共用规则／状态 → 平台执行与恢复”的现有边界。
- 改组目标是让新增系统适配尽量集中于对应适配实现和验证记录，减少散落全库的系统判断。
- 系统名称用于用户理解；实际接入仍需核对组件与 ABI，不能仅凭设备品牌或 build fingerprint 决定兼容与授权。
- 不为尚不存在的实现建立庞大插件框架；用现有社区 PR 作为真实适配样本，按实际缺口逐步整理。
- 完善从识别接入点、实现、测试、提交到 Review 的贡献文档，明确新增作用域、权限、协议和认证／电源行为变化需单独讨论。
- 贡献者应能使用测试签名构建验证；正式签名只进入维护者的可信发布流程，不提供给外部 PR。
